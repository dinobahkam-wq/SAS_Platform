# SAS Daily Briefing — Public Experience V1

**الحالة:** تنفيذ أولي على فرع مستقل؛ بانتظار الاختبار المحلي.  
**المسار العام:** `/briefings`، `/briefings/[slug]`.  
**الفرع:** `feat/daily-briefing-public-experience-v1`.  
**قاعدة البيانات:** قراءة فقط عبر RPCs العامة الموجودة في Package 1.

## 1. القرار التحريري المحدث

المنتج في إطلاقه الأول مرصد معلوماتي يومي يركز على سجل التطورات، لا نشرة رأي لمنصة ساس.

الأولوية:
1. التطورات والوقائع الموثقة.
2. البيانات والتصريحات والمواقف منسوبة إلى أصحابها.
3. الادعاءات مع توضيح أنها روايات منسوبة وغير مثبتة مستقلًا.
4. المصدر الأصلي وتاريخه بجوار كل تطور.
5. موجز تنفيذي وصفي قصير يساعد القارئ على التقاط أهم ما ورد.
6. مساحة تفسيرية لساس اختيارية وثانوية ومنفصلة بصريًا عن سجل الوقائع.

لا تُعرض وجهة نظر المنصة باعتبارها حقيقة، ولا يُستنتج تبني ساس لموقف لمجرد توثيقه.

## 2. مسارات الجمهور

### `/briefings` — الأرشيف
- تعريف موجز بالمنتج ومنهجه.
- أحدث عدد منشور في مقدمة الأرشيف.
- قائمة الأعداد المنشورة السابقة.
- لا تظهر المسودات أو النسخ قيد المراجعة.
- حالة فارغة صريحة إذا لم يوجد عدد منشور؛ لا محتوى تمثيلي أو أخبار وهمية.

### `/briefings/[slug]` — قراءة العدد
1. العنوان ورقم العدد وتاريخه.
2. نافذة التغطية بتوقيت اليمن، وقت آخر تحقق، وتاريخ النشر.
3. توضيح أن تصنيف المعلومة لا يعني تبني المنصة لمضمونها.
4. خلاصة وصفية موجزة، إن وجدت.
5. **سجل التطورات بوصفه القسم المركزي والأوسع.**
6. لكل تطور: التصنيف، النطاق الجغرافي، توقيت الوقوع، عنوان محايد، ملخص، تفصيل التغير، حالة التحقق، ومصادره الأصلية.
7. فهرس موحد للمصادر في نهاية العدد.
8. منهجية وحدود التغطية داخل قسم قابل للفتح.
9. قراءة ساس في قسم منفصل ومغلق افتراضيًا، إذا توفرت.

## 3. قواعد العرض

- العربية وRTL، متجاوب للهاتف والحاسوب.
- لا صور إخبارية في V1.
- Tajarib Taweel للعناوين وThmanyah Sans للمتن والبيانات.
- الأرقام اللاتينية.
- المصدر بجوار التطور، مع رابط خارجي آمن عند وجود URL صالح.
- تمييز FACT / POSITION / CLAIM / ANALYSIS، وحالة التحقق منفصلة عن نوع المعلومة.
- عرض وقت وقوع الحدث مستقلًا عن تاريخ نشر المصدر.
- لا تُعرض خانة فارغة إذا لم تتوفر معلومة.
- لا تعرض الواجهة حقولًا تفسيرية مثل "لماذا يهم؟" بوصفها عنصرًا إلزاميًا؛ يظل السجل خبريًا/معلوماتيًا.

## 4. التنفيذ الأولي

- `src/lib/public-briefing.ts`: قراءة RPCs وتطبيع JSON وتصفية روابط المصادر إلى HTTP/HTTPS.
- `src/components/briefing-public.tsx`: مكونات التصنيف والمصدر والتاريخ وبطاقات الأرشيف.
- `src/app/briefings/page.tsx`: الأرشيف العام.
- `src/app/briefings/[slug]/page.tsx`: قارئ العدد العام.
- `src/components/public-site.tsx`: إضافة الإحاطة إلى التنقل العام.
- `src/app/globals.css`: تنسيق عام متجاوب خاص بالإحاطة.

## 5. الأمن ومصدر البيانات

- لا قراءة مباشرة من جداول `briefing_*` في واجهة الجمهور.
- استخدام `get_public_briefing_archive` و`get_public_briefing` فقط.
- RPCs تعيد الأعداد المنشورة ولقطات النشر؛ لا تعرض المسودات.
- لا Service Role Key في الواجهة أو في طبقة القراءة.
- روابط المصادر لا تُفتح إلا إذا كان البروتوكول HTTP أو HTTPS.
- لا كتابة إلى Supabase من صفحات الجمهور.

## 6. تعارض يحتاج حسمًا قبل أول نشر

Migration Package 1 الحالية تفرض على قاعدة البيانات أن:
- `analysis_ar` حقل إلزامي غير فارغ.
- دالة النشر ترفض القراءة التحليلية التي تقل عن 400 كلمة أو تتجاوز 650 كلمة.

هذا الشرط لا ينسجم تمامًا مع التوجه التحريري الجديد الذي يجعل تحليل ساس محدودًا واختياريًا. في التنفيذ الحالي أخفينا القراءة التحليلية داخل قسم مغلق أسفل سجل التطورات، لكن هذا لا يلغي قيد قاعدة البيانات.

**المقترح للمراجعة:** تعديل لاحق يسمح بأن تكون قراءة ساس اختيارية، أو ملاحظة سياقية قصيرة لا تتجاوز 150 كلمة، مع الإبقاء على إلزامية سجل التطورات والمصادر والتحقق. لا تُطبق أي Migration لتغيير هذا القيد على Supabase الإنتاجية قبل موافقة المستخدم على السياسة والنص المقترح.

## 7. حالة البيانات والاختبارات

- تحقق مباشر من Supabase: `briefing_editions = 0` و`published revisions = 0`؛ الأرشيف العام يعيد `[]`.
- لذلك تعرض الواجهة حاليًا حالة فارغة صحيحة.
- لم تُنشأ بيانات تجريبية ولم يُنشر محتوى.
- لم يُنفذ `typecheck` أو `build` محليًا على Windows بعد هذه التغييرات.
- لا PR ولا دمج ولا نشر Vercel حتى الآن.
